### 2026-08-18 — Full security/bug/efficiency hardening pass from a developer review
- **Why:** a developer reviewed the codebase and flagged 8 "critical" security items, 11 functional bugs, 6 efficiency notes, and 6 code-quality notes in a spreadsheet. Each item was verified against the actual current code before fixing anything — some were real, some were already-deliberate decisions (not bugs), and at least one ("GBP imageUrl SSRF") turned out to be a misread of code that never actually accepts attacker input. The project owner asked to fix everything real and to proactively cross-check for anything the review missed.
- **What the crosscheck found that the review didn't:** `WHATSAPP_VERIFY_TOKEN` has the exact same "real value with a public dev default, no production guard" shape as `WHATSAPP_APP_SECRET` (which the review DID catch) — fixed both the same way `JWT_SECRET` already was. Also found that `clients/gbp-oauth.ts`'s static-token fallback triggered not just when a business had no OAuth at all, but also on a *transient* failure of a real business's own token exchange — meaning a Google API hiccup could silently post that business's content using the shared pilot account's token, to the wrong Google Business Profile entirely. Fixed to never fall back once a real refresh_token exists.
- **Two onboarding fields removed, not patched — the review found the symptom, not the actual fix:** `mixpostAccountIds` and `gbpRefreshToken` were both settable by a business through its own self-serve onboarding PUT. `mixpostAccountIds` had no cross-check against Mixpost's own workspace, so a business could type in another business's connected account ID and (with one shared `MIXPOST_TOKEN`) get us to publish there. `gbpRefreshToken` let a business paste in *any* string directly, completely bypassing the real Google OAuth consent flow that's supposed to be the only way this ever gets set (and was leftover from before that flow existed). Both moved out of self-serve entirely — Mixpost account linking is now admin-only (`POST /api/admin/businesses/:id/mixpost-accounts`, set only after an admin manually verifies the connection inside Mixpost's own dashboard); `gbp_refresh_token` is now set exclusively by the real OAuth callback.
- **The worker's publish loop is now a real atomic claim, not a plain SELECT.** `FOR UPDATE SKIP LOCKED` + marking rows `'publishing'` inside a short transaction (new `post_status` enum value, migration `007`) before any external API call — closes a genuine double-publish race if this worker is ever scaled beyond one instance, which it isn't today but the fix costs nothing to have in place now. Any post that hits an unexpected error after being claimed reverts to `'scheduled'` rather than getting stuck.
- **The exact bug already fixed once for empty `mixpost_account_ids`, found again in a second form:** when Mixpost is entirely unconfigured, `schedulePost()` dry-runs and used to return the same shape as a real success — so the worker marked posts `'published'` when nothing had actually gone out. Added a `dryRun` flag; the worker now reverts to `'scheduled'` instead, matching the existing "no accounts connected" precedent.
- **Cost-incurring routes got the rate limits they were missing.** `/api/audit/run` already had a tight per-route limit for exactly this reason (real LLM/Places cost per call) — `/gbp/post` and `/social/schedule` cost the same per call and never got the same treatment. Added a 10/min limit to both, plus a 300-char cap on the free-text `focus`/`occasion` fields that go straight into a prompt.
- **`profile_context` sanitization, extracted to its own pure module** (`features/content/sanitize.ts`, not left inline in `generator.ts`) specifically so it's unit-testable without needing `DATABASE_URL` set (`generator.ts` imports `db.js` at module scope). Strips control characters, hard-caps serialized size at 4000 chars. Real fix, narrower scope than the review implied — a business can only ever manipulate its own generated content, nothing cross-tenant sits in this prompt.
- **Smaller fixes bundled into the same pass:** GBP posts now hard-truncate at 1500 chars (Google's own Local Post limit) instead of just asking the LLM nicely; a 60-second debounce prevents a double-click from creating two GBP posts; stale `'draft'` posts (publish never attempted/failed, no cleanup) now get deleted after 30 days by a new daily worker job; added a `DELETE /api/businesses/:id/gbp/connection` endpoint (attempts to revoke at Google's end too, not just clear our own copy) since there was previously no way to sever a compromised refresh_token short of a manual DB edit.
- **Also fixed, unrelated to any specific finding:** `clients/gbp-oauth.ts`'s header comment was badly stale — described a manual OAuth-Playground copy-paste workflow and the now-removed `gbpRefreshToken` field as if they were still current, and referenced `Technical-Setup-Guide.md` (the same nonexistent file already fixed elsewhere this session). Rewritten to describe the real, current flow.
- **What was reviewed and deliberately left alone, because it was already a decision, not an oversight:** quality-tier-always for social posts, `setInterval` instead of a job queue, and per-request (not cached) entitlement checks are all explicitly documented design choices elsewhere in `DECISIONS.md`, not accidental gaps — re-litigating them wasn't part of this pass.
- **Status:** implemented. Typecheck and the full test suite (including 4 new unit tests for the sanitizer) pass. **Not yet verified against a live database or real Mixpost/GBP/Meta traffic** — the atomic-claim query and the debounce guard in particular deserve a real run before full trust.

### 2026-08-18 — WhatsApp customer self-service menu (My Stats + Get a Website)
- **Why:** the project owner shared screenshots of a competitor's (Grexa) WhatsApp bot, which uses genuine interactive messages (reply buttons, rich cards) to run its whole onboarding script — and asked for something more advanced: an existing customer should be able to get their dashboard stats and request a website entirely from WhatsApp. Checking our own bot first turned up a foundational gap, not just a feature gap: `clients/whatsapp.ts` only ever supported `sendText`/`sendTemplate`, and `routes/whatsapp.ts` only ever read `msg.text.body` — a button tap (`msg.interactive.button_reply`) was invisible to the code entirely. We were behind the competitor's baseline UX, not ahead of it.
- **Purpose:** close that foundation gap and ship the two specific asks on top of it, without over-building (no new NLU, no new chart-rendering infra, no new CRM integration where a much smaller fix does the same job today).
- **Phase 1 — interactive messages + telling an existing customer apart from a new lead.** Added `sendButtons()`/`sendList()`/`sendImage()` to `clients/whatsapp.ts`; `routes/whatsapp.ts` now reads `msg.interactive.button_reply?.id ?? msg.interactive?.list_reply?.id` alongside `msg.text.body`. Critically, inbound messages to our own platform number now branch three ways, not two: a business's own customer (matched on `businesses.whatsapp_number`) → `handleChatAgent` (unchanged); an existing owner (matched on `users.phone`, role='owner' — a DIFFERENT number by design, see `FLOW.md` §10) → the new `handleCustomerMenu`; anyone else → the existing lead-gen flow (`handleMessage`, unchanged). This lookup is what makes "an existing customer can self-serve their own stats" possible at all — without it, every inbound message would fall into the new-lead script.
- **The customer menu is deliberately stateless** — no new Redis conversation state. Every message either matches a known button id (`view_stats`, `want_website`) or falls through to showing the menu again. Simpler than the audit bot's Redis-backed state machine, and correct for this flow: there's no multi-step sequence to remember between messages.
- **Phase 2 — "My Stats": reuses the ROI dashboard's own data and view, no new query.** `features/insights/whatsapp-stats.ts` queries the exact same `v_monthly_enquiries` view `/api/businesses/:id/roi` already does. Rendering: **QuickChart** (open source, `github.com/typpo/quickchart`, self-hostable — same pattern as Kuma/Twenty on the home lab, defaulting to their hosted free instance for now) rather than a headless-browser screenshot (Puppeteer) — a real dependency-weight decision, not a default. The rendered PNG is uploaded via the **same R2 client already built for AI post images** (`clients/storage.ts`) — no changes needed there, it already just takes any buffer + key and returns a public URL. Gated on the same `hasMinPlan('starter')` check as the rest of the chat agent — a lapsed owner shouldn't get this either. Falls back to a plain-text summary if chart rendering or upload fails, rather than going silent.
- **Phase 3 — "Get a Website": a flag on `businesses`, not a `leads.stage` value.** `db/migrations/006_website_requests.sql` adds `businesses.website_requested_at`. Deliberately NOT on `leads` — wanting a website isn't a sales-pipeline stage (it can co-exist with any stage), and more importantly, the actual trigger point here (an existing paying customer via the new menu) often has no `leads` row at all: a business created via the pay-first checkout flow (`DECISIONS.md`, Chunk C) never gets a `leads` row in the first place. Scoped to existing customers only this round — extending the same button into the pre-signup lead-gen flow (where a `leads` row *does* exist) is a small, separate follow-on if wanted later, not built now.
- **"Notify a human": WhatsApp alert + email now, Twenty CRM integration deliberately deferred — the project owner's explicit call, going with the recommended option.** The "proper" long-term answer is pushing this into Twenty (set up on the home lab earlier this session) as a deal, but that means building a real Twenty API client (auth, field mapping) — a distinct, bigger piece of work from "make sure a human finds out." `features/leads/website-request.ts` sends both: a WhatsApp template to `OPS_ALERT_PHONE` (skipped with a warning if `WHATSAPP_WEBSITE_REQUEST_TEMPLATE_NAME` isn't approved yet — same unresolved-template situation as renewal reminders and payment confirmations) and an email to `OPS_ALERT_EMAIL` via the already-built SES client (works today, no external approval needed) — so the feature is actually usable immediately, not blocked on Meta approval like the WhatsApp side is.

### 2026-08-18 — Weekly auto-posting, image generation, Facebook fix, Pro plan dropped
- **Why:** a pricing-vs-reality audit (this session, same day) found the product's core automation promise wasn't real — "weekly" GBP/social posts required a human to click a button every time, Facebook wasn't reachable from the dashboard at all despite being sold, "booking microsite" overstated a plain enquiry page, and "multi-branch/multi-location" (Pro plan) had zero backing in the schema. The project owner's explicit goal is a low-manpower automation business — a human-triggered "automation" feature doesn't serve that goal or scale with paying customers.
- **Six decisions, all confirmed by the project owner:**
  1. **Fix the Facebook button** — trivial, backend already supported the channel.
  2. **Build real weekly auto-posting**, but it must re-check entitlement on every run so a lapsed business's generation stops immediately — no exceptions.
  3. **WhatsApp templates — explicitly not touched this round** (project owner: "will work on later, i didnt touch it till now"). Nothing changed for campaigns.
  4. **Booking microsite stays a claimed feature** — the project owner is committing to wiring in Cal.com later; no code change needed today, the existing enquiry microsite remains as-is.
  5. **Pro plan dropped entirely** — cannot honestly claim multi-location support that doesn't exist. Removed from pricing, the admin checkout tool, and the sellable-plan enums. The Postgres `plan_tier` enum and the TypeScript `PlanTier` type/`PLAN_RANK` in `entitlement.ts` were deliberately **left untouched** — ripping a value out of a live enum for zero functional benefit is a disruptive migration for something that's inert if simply never sold again.
  6. **Image generation added** for GBP + Instagram + Facebook only — not campaigns/chat (text-only), and explicitly not X/LinkedIn (project owner's own call: "mostly businesses dont use it").
- **Two cross-cutting constraints, both explicitly required by the project owner:**
  - **Security — no generation for lapsed businesses, ever.** The new weekly auto-post job (`worker.ts`'s `checkWeeklyAutoPosts()`) is the only new thing capable of spending money/LLM calls without a human clicking anything, so it re-runs `getEntitlement()` fresh for every candidate business on every single run (every 6h) — never a cached or one-time check. A business that lapses between runs simply stops appearing as entitled; nothing special has to happen to "turn it off." Same live-check pattern `auth/entitlement.ts` already uses everywhere else — no new security logic invented, no new way for it to be wrong.
  - **Data/memory retained for returning customers.** Checked before building anything: there is no data-purge or cleanup job anywhere in this codebase. Cancelling only ever changes `businesses.status`; nothing deletes `posts`, `profile_context`, or anything else. So a business that lapses and resubscribes months later already keeps its full post history (and therefore the "recent posts" memory built earlier this session) automatically — nothing needed to be built for this, it just needed confirming, and flagging here so nobody adds a purge job later without re-reading this.
- **Weekly auto-posting: how the topic gets chosen without a human.** `generateSocialPost`/`generateGbpPost`'s `focus` parameter is now optional — when omitted, the prompt tells the model to pick a fresh angle itself using the business's `profile_context` and (for social) the same "last 8 posts" memory block built earlier this session. This reuses that memory mechanism for a second purpose (freshness *and* now topic selection) rather than building a separate curated topic-rotation list.
- **Image generation: the real complexity was storage, not generation.** OpenRouter's image endpoint (`POST /api/v1/images`, confirmed via its docs this session) returns base64 bytes, not a hosted URL — but Mixpost (`clients/mixpost.ts`) and GBP's `localPosts.media` both require a real public URL to actually publish an image, not inline data. Added `clients/storage.ts` — Cloudflare R2 via `@aws-sdk/client-s3` (S3-compatible; same "don't hand-roll AWS SigV4" exception already established for SES, and the same vendor already planned for DB backups in `infra/backup.sh`). Requires the project owner to create one R2 bucket + API token manually (same shape as the `TWENTY_ENCRYPTION_KEY` setup) — empty R2 config silently no-ops image generation rather than breaking caption-only posting.
- **Model choice:** `black-forest-labs/flux.2-klein-4b` via OpenRouter — confirmed live pricing (~$0.014/megapixel) and exact slug against OpenRouter's own model pages in this session before defaulting to it, same verify-before-trusting-a-slug pattern used for the Claude Haiku default earlier this session.
- **Image generation is best-effort, never blocking.** `clients/image.ts`'s `generateImage()` returns `null` (never throws) on any failure — a flaky image API or unconfigured R2 must never prevent the caption/text post itself from generating and publishing.
- **GBP posts never had a `media` field wired up at all** (found while adding this) — GBP's Local Posts API supports one; added `media: [{ mediaFormat: 'PHOTO', sourceUrl }]` to the publish call. Flagged with a comment to verify the exact request shape once real GBP API access is approved (unverified against a live Google account, same as the rest of `gbp/service.ts`).
- **Status:** implemented. Typecheck, existing test suite, and `next build` all pass. **Not yet verified against real OpenRouter/R2/Mixpost/GBP credentials or a live database** — no live services available in this session.

### 2026-08-18 — Social posts: quality-tier model + per-business content memory
- **Why:** the project owner raised two doubts about the social scheduler: (1) use a better LLM model via OpenRouter, (2) give it "memory" of what it already generated for a business so it doesn't repeat itself and writes more engaging, continuous content over time.
- **Checked before proposing anything:** `generateSocialPost()` was the only customer-facing content type in `features/content/generator.ts` still on the `cheap` tier — GBP posts and campaign messages were already on `quality`. No content-generation call anywhere had access to a business's own past output; only the static `profile_context` (services/pricing/offers). No image generation exists anywhere in the codebase — `visualIdea` is a one-line text tip for the owner to shoot a photo themselves, not an AI-generated image. Flagged this last point explicitly since the project owner's phrasing implied images might already exist.
- **Two forks, decided by the project owner via question tool:**
  1. **Quality-tier model applies to all plans**, not gated to Growth+/Pro — same reasoning already applied to GBP posts and campaign messages (public brand content either way).
  2. **Scope stays text + memory only this round** — real AI image generation (a new API integration, real per-image cost, using the already-existing-but-unused `posts.media_urls` column) is explicitly deferred as its own future decision, not built now.
- **"Memory" = the business's own last 8 social captions, already sitting in `posts`, fed into the prompt.** No new table, no vector DB, nothing shared across businesses or customers — `loadRecentSocialCaptions()` queries `WHERE business_id = $1 AND channel IN ('instagram','facebook')`, deliberately excluding GBP posts (different tone/platform, same table). This is genuinely bounded and cheap: a business posts a few times a week, so "last 8" is only ever a few weeks of short captions, regardless of how long the business has been a customer.
- **Scoped narrowly to `generateSocialPost()` only** — not GBP posts, campaign messages, or the WhatsApp chat agent, despite all four sharing this file's `SYSTEM` prompt (see `FLOW.md` §4's blast-radius warning). Extending memory to those is a reasonable future ask but wasn't requested; doing it by default here would have been unrequested scope creep into shared, customer-facing prompt behavior.
- **Two bugs found and fixed while doing this** (see `BUG.md`): OpenRouter's model IDs were hardcoded, silently ignoring OpenRouter's own multi-model access (it was only ever actually calling Gemini); and `posts.generated_by` — the cost-tracking column — always recorded the literal string `'gemini-cheap'` regardless of what actually ran.
